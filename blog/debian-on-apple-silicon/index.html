Running Debian on Apple Silicon: What's Different from Ubuntu

Second in the series on specific Linux distributions. Debian runs natively on arm64 like Ubuntu, but its installer and networking defaults are different, and in Velo Workspaces the fast path is the official cloud image.

Same CPU story, different defaults

Debian on an Apple silicon Mac runs the way Ubuntu does: natively on arm64. Debian 13 "Trixie", the current stable release, ships arm64 as a fully supported architecture alongside amd64, riscv64 and the rest, not as a best-effort port.

You may have read that Debian 13 added drivers for Apple silicon MacBook hardware. That work is for installing Debian directly on the Mac (the Asahi Linux route). A Debian guest in a VM never touches the Mac's trackpad or keyboard controller, so none of it applies here.

The quick way: Debian's official cloud image

Choose Cloud image when you create a workspace and pick Debian 13 or Debian 12. Velo Workspaces downloads Debian's generic arm64 image from cloud.debian.org, checks it against Debian's SHA-512 checksums, and passes your username, password and this Mac's SSH key to cloud-init. On first boot Debian creates your account, grows its disk to the size you chose, and is ready in about a minute.

One detail if you're comparing notes with other tools: Velo Workspaces uses the generic image, not genericcloud. The genericcloud kernel leaves out the virtio GPU driver, so its display stops at "EFI stub" while the system carries on booting headless. The generic image gives you a working console as well as SSH.

The installer, by hand

If you'd rather run Debian's installer, choose Installer image and pick the Debian 13 netinst or DVD ISO. Debian's installer isn't automated in Velo Workspaces yet: its answer file (preseed) has to come from a boot argument or from inside the installer's own initrd, which needs a different approach from Ubuntu's and Fedora's. So you go through debian-installer yourself in the workspace's display: locale, keyboard, mirror, partitioning, then tasksel for package sets. Ubuntu's installer asks fewer questions, but neither is hard. For a hands-free Debian, use the cloud image.

Networking: no Netplan, so Ubuntu's clone gotcha usually doesn't apply

The Ubuntu post describes a workspace cloned from an Ubuntu Server base image coming up with no IP address, because Netplan matches the interface by the base image's old MAC address. That's a Netplan behavior, not a general cloning problem. A Debian system set up by debian-installer uses ifupdown and /etc/network/interfaces, which refer to interfaces by name (enp0s1), so a clone with a new MAC address keeps working.

Cloud images are configured by cloud-init instead. If you save one as a base image and a clone comes up without a network, look for a MAC address match in /etc/netplan/ or /etc/network/interfaces.d/; the fix is the same as Ubuntu's.

Rosetta, briefly

Debian registers Rosetta the same way Ubuntu does, with apt and update-binfmts: mount the rosetta VirtioFS share, install binfmt-support, and register it with Apple's magic bytes and mask. The support FAQ has the exact commands. The caveat from the Ubuntu post applies here too: Rosetta translates a single binary well, but it can't create x86-64 packages that were never built for arm64.

Debian or Ubuntu?

Both are good choices for a dev, QA or DevOps workspace; the difference is what you want to optimize for. Debian moves slowly on purpose. Packages change less often, which is what you want when a base image should stay predictable for months. Ubuntu usually has newer packages and is what most tutorials and CI configs assume. With no strong reason either way, Debian's small footprint and conservative base make it a sensible default for a long-lived base image.
