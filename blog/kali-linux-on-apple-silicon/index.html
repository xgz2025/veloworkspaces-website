Running Kali Linux on Apple Silicon

Kali Linux ships an official arm64 build, and Velo Workspaces 1.2 downloads it for you. Here's how the install goes, and the networking detail to understand before you rely on it for testing.

By Gaoliang Luo · Published September 22, 2026 · Updated September 29, 20262 min read

Step by step, with screenshots: install Kali Linux and turn on SSH, every screen shown.

An official arm64 build, and the right file to use

Kali Linux, maintained by OffSec, publishes generic arm64 installer ISOs next to a long list of images for specific single-board computers. For a VM you want the generic installer. The Raspberry Pi and other board images carry hardware-specific kernels and won't boot in a virtual machine.

In the catalog, installed by hand

Velo Workspaces 1.2 has Kali in its catalog, so you don't have to find the right file yourself. Create a workspace, choose Installer image and pick Kali Linux; the app downloads the current arm64 installer from Kali's servers and checks it against Kali's published checksum. Kali's installer is debian-installer, and like Debian's it isn't automated yet, so you go through it yourself in the workspace's display: your user, partitioning, and which tool sets to install.

A Kali cloud image that sets itself up on first boot is on the roadmap for a 1.2.x update. Kali publishes it as a compressed archive rather than a disk image, so the app needs to unpack it first.

NAT networking, and what it means for a lab

Velo Workspaces uses NAT networking only; bridged networking needs an entitlement the app doesn't have, as the Virtualization.framework post explains. For most Linux guests you'd never notice. For Kali it matters more, because much of the toolkit is meant for scanning and testing other devices on your network. Behind NAT, the guest sits on the Mac's private virtual network, not your LAN. Tools that connect out to a target by address work; tools that expect to share a network segment with their targets, like ARP scans, won't see them. Check what a tool needs before you build a workflow on it.

Why disposable workspaces suit a testing lab

Tools, scan results and artifacts from one engagement have no business carrying over into the next, and a lab that has piled up months of leftovers makes it hard to say you tested from a clean baseline. Install and configure Kali once, save it as a base image, and start each engagement from a fresh disposable workspace cloned from it. Closing it deletes it, and the next one starts from exactly the same state. Base images as versioned infrastructure covers the base-image half of that.
